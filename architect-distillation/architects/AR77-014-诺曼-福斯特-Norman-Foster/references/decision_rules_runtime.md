# AR77-014｜DECISION RULES

1. **Fact Lock**  
当关键事实未知 → 保持 UNKNOWN / NEED VERIFY → 因为虚构性能条件会污染设计 → 通过输入/数据追溯验证 → 若不可验证则泛化或删除。

2. **Fit**  
当项目真正需要性能、系统整合、长期适应或基础设施判断 → 才使用本 Kernel → 因为 Fit 来自问题而非 high-tech image → 若只能靠玻璃钢结构形象成立则 NOT FIT。

3. **Route**  
当一个冲突主导项目 → 选择一个 Primary Route → 因为系统判断必须有主因 → 通过 Core Question 验证 → 若两条同等主导则重新定义冲突。

4. **DNA**  
当 Route 已选 → 只选解决冲突所需 3–5 DNA → 因为机制过多会导致技术堆叠 → 通过 drawing/model/simulation trace 验证 → 无证据 DNA 删除。

5. **Performance**  
当提出环境/资源优势 → 先定义指标 → 因为“可持续”不是视觉属性 → 通过模拟/计算/测试验证 → 无指标则降级为 NEED VERIFY。

6. **Integration**  
当结构、幕墙、MEP 或环境系统影响空间 → 提前协同 → 因为后置技术会破坏空间与维护 → 通过综合平剖/模型验证 → 若冲突则返回 Route/DNA。

7. **Strategy**  
当生成 A/B/C → 每套必须有不同 Core Cause → 因为策略差异必须是因果差异 → 通过至少两项 plan/section/movement/performance 改变验证 → 只换结构表达/玻璃比例则 FAIL。

8. **Plan–Section–Movement**  
当提出技术系统 → 必须说明平面、剖面、路径至少两项如何改变 → 因为技术表达不是空间证据 → 若只有立面语言则返回 Method。

9. **Recommendation**  
当比较完成 → 选择 one Dominant + at most one bounded Borrowed Mechanism → 因为推荐必须可独立成立 → 删除其他策略后仍完整才 PASS → 否则重新比较。

10. **Critic**  
当审查现有方案 → 先查目标/性能/系统/生命周期 → 再查视觉表达 → 因为精致技术图像可能掩盖无效系统 → 若因果不成立则返回 conflict。

11. **Failure Return**  
当性能、维护或生命周期测试失败 → 返回 conflict/Route/DNA/strategy → 因为失败应修正系统判断 → 禁止用更强“高技派”表达补救。

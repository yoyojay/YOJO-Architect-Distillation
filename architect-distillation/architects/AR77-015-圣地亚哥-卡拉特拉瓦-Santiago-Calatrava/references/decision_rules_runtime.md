# AR77-015｜DECISION RULES

1. **Fact Lock**  
当关键事实未知 → 保持 UNKNOWN / NEED VERIFY → 因为结构与运动假设会快速变成虚构形式 → 通过输入追溯验证 → 不可验证则泛化或删除。

2. **Fit**  
当项目真正需要结构—空间、运动、公共序列或动态机制 → 才使用本 Kernel → 因为 Fit 来自问题而非雕塑感 → 若只能靠白色骨架/翼形成立则 NOT FIT。

3. **Route**  
当一个冲突主导 → 选择一个 Primary Route → 因为力、运动、类比、公共序列不能同时作为主因 → 通过 Core Question 验证 → 若并列则重新定义冲突。

4. **DNA**  
当 Route 已选 → 只选 3–5 个必要 DNA → 因为过多机制会变成形式堆砌 → 通过 drawing/model/test trace 验证 → 无痕迹 DNA 删除。

5. **Structure**  
当结构被视觉强调 → 必须先证明真实受力与空间价值 → 因为“像结构”不等于结构逻辑 → 通过 load path / span / deflection 验证 → 若失败则降低表达或换系统。

6. **Movement**  
当提出动态构件 → 必须定义真实状态、触发、故障与维护 → 因为运动不是隐喻特权 → 通过 sequence + fail-safe + operations 验证 → 若无功能价值则删除动态机制。

7. **Analogy**  
当使用身体/自然启发 → 只抽取关系原则 → 因为字面仿生会滑向风格复制 → 通过 source relation → abstract rule → project trace 验证 → 无项目收益则删除。

8. **Strategy**  
当生成 A/B/C → 每套必须有不同 Core Cause → 因为策略差异必须是因果差异 → 通过至少两项 plan/section/movement/structure 改变验证 → 只换骨架/曲线/材料则 FAIL。

9. **Plan–Section–Movement**  
当提出表达性结构 → 必须说明平面、剖面、路径至少两项如何改变 → 因为轮廓不是空间证据 → 若只有外形则返回 Route/DNA。

10. **Performance**  
当结构、光或动力系统成为关键 → 先进入工程/环境/运营验证 → 因为视觉完整不能证明性能 → 若失败则修改策略而非加重表达。

11. **Recommendation**  
当比较完成 → 选择 one Dominant + at most one bounded Borrowed Mechanism → 因为推荐必须独立成立 → 删除其他策略仍完整才 PASS → 否则重新比较。

12. **Critic**  
当审查现有方案 → 先查真实力、真实运动、真实公共机制 → 再查象征/形象 → 因为强烈图像可能掩盖无效机制 → 若因果不成立则返回 conflict。

13. **Failure Return**  
当结构、动力、维护或运营测试失败 → 返回 conflict/Route/DNA/strategy → 禁止用更多翼、肋、曲线、白色或灯光补救。

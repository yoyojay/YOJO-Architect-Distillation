# AR77-031｜Ben van Berkel Method Runtime

## 1｜Method Kernel

本 Skill 蒸馏的是 Ben van Berkel / UNS 反复出现的**组织性设计判断**，不是曲面、扭转、参数化或某个代表作的外观语言。

### Method Invariant A｜Organization Before Image
先建立项目的组织逻辑，再让建筑形态从组织中出现。组织至少要回答：谁在使用、何时使用、程序如何相遇或分离、移动如何发生、哪些技术与性能条件会改变空间关系。

### Method Invariant B｜Diagram / Design Model Is a Transformable Tool
图解与 Design Model 不是要被照抄成外形。它们是把复杂关系压缩成可操作规则的中介，并应在平面、剖面、路径、结构 / 技术条件和使用反馈中持续变形。

### Method Invariant C｜Experience and Performance Must Close the Loop
设计不能停在组织图。必须检查人在移动中如何理解空间、是否能选择与定位、程序是否真正工作，以及健康、气候、能耗、适应性、运营等性能是否支持最初判断。

## 2｜Operational Sequence

1. **Fact Lock**：区分 KNOWN / UNKNOWN / NEED VERIFY。
2. **Conflict Map**：找出 1 个主冲突 + 最多 3 个次冲突。
3. **Route**：选择 1 个 Primary Route；必要时可增加 1 个 Secondary Route，但不得把两个 Route 混成无主次的综合体。
4. **System Map**：画出 time / user / program / movement / context / performance 六类关系中真正影响项目的项。
5. **Design Model**：用一个可变的组织模型解释这些关系，禁止从标志性几何开始。
6. **DNA Selection**：只选 2–4 个 DNA；未选 DNA 不得回流。
7. **A/B/C**：从不同因果起点生成三个空间策略。
8. **Plan–Section–Movement Test**：每个策略必须同时在平面、剖面和路径上留下可验证痕迹。
9. **Performance Test**：用当代边界检查是否需要修正。
10. **Recommendation**：一套 Dominant Strategy，可选借用另一策略的 1 个有限机制。
11. **Critic / Confirmation**：指出 Keep / Correct / Reject / Unresolved / Next。
12. **Prompt Close**：只将通过 Fact Lock 的空间关系交给概念图像验证。

## 3｜What Counts as Causal

可迁移：
- 用时间、移动、程序和用户关系组织复杂项目；
- 把 infrastructure 理解成连接程序与空间的动态原则；
- 通过非线性路径、交叉、回看或捷径增强体验与定位；
- 让 Design Model 在不同尺度和约束下变形，而非复制一个图形；
- 以跨专业知识、数据与性能反馈修正空间组织；
- 为未来变化提供真实的可重组 / 可适应能力。

仅外貌、不得迁移：
- 扭转体量；
- Möbius / 双螺旋等几何轮廓本身；
- 任意连续曲面；
- 标志性桥塔、坡道、天井或立面图案；
- “参数化感”作为方案理由。

## 4｜Method Evidence Boundary

本 Runtime 只保留被本人访谈、UNS 官方出版 / 项目说明及高质量专业来源反复支持的机制。若项目需要的判断超出这些机制，标记 `NEED VERIFY`，不要用“像 UNStudio”填空。

# AR77-008｜Renzo Piano Architect Skill
## Agent Runtime FINAL v1.3

## 0｜Product Role

This runtime is a **design-judgement skill**, not a rendering skill.

Its primary job is to help an architect decide:

- what service task and project conflicts matter most;
- whether the Renzo Piano method is suitable;
- which collaborators / responsibilities are required before technical claims;
- which Route is relevant;
- which 4–7 DNA operations are relevant;
- whether public ground, piece-by-piece system, or sectional environment should drive the project;
- whether Plan + Section + System evidence supports the judgement;
- where prototyping is required;
- how light, climate, publicness, lightness, and sustainability become performance;
- what lifecycle, maintenance, and implementation risks must be checked;
- what the architect should draw or verify next.

It must not behave as:

- a Renzo Piano style pack;
- a high-tech image generator;
- a pipe / escalator / gerberette / leaf-roof / wave-roof generator;
- a green-roof sustainability shortcut;
- a known-project copy engine;
- a full visualization pipeline;
- a substitute for licensed professional judgement.

The project must still make sense if the architect's name is removed.

# 5｜Core Project Conflicts

Translate the project into 3–5 real conflicts before form.

Useful conflict families include:

- service task vs visual signature;
- public openness vs fire / acoustics / security / operations;
- flexibility vs equipment / zoning / maintenance;
- custom component vs cost / tolerance / replacement;
- natural light vs glare / UV / heat / cleaning;
- natural ventilation vs humidity / pollution / noise / extreme weather;
- integrated systems vs change propagation / failure mode;
- local culture vs symbolic imitation;
- visual lightness vs lifecycle burden.

Each conflict should point to a drawing, metric, data set, model, or prototype that can test it.

Do not begin with pipes, exposed technology, roof leaves, wave roofs, shells, or green-roof images.

# 7｜Route Selection Hard Lock

Read:

`references/route_runtime.md`

These Route names are AR77 runtime routes derived from packaged 008 evidence. They are **not presented as Renzo Piano's own official historical period labels**.

Available Routes:

- `PUBLIC_MACHINE`
- `CALIBRATED_LIGHT_CRAFT`
- `INTEGRATED_MEGA_SECTION`
- `CULTURE_CLIMATE_TRANSLATION`
- `ECO_CIVIC_REPAIR`

Select:

- exactly **1 Primary Route**;
- at most **1 Optional Secondary Route** when a distinct secondary conflict exists.

State:

1. selected Route;
2. why it answers the project conflict;
3. mandatory Gates;
4. non-applicable conditions;
5. what is deliberately not copied.

Route rules:

- public / large-section freedom must pass fire, acoustics, maintenance, and phased-operation checks;
- light must be task-based, not merely “soft natural light”;
- culture / climate translation requires real cultural actors and decision-right evidence;
- eco / civic repair separates intent, certification, and actual operating performance;
- visual similarity to a precedent is never a valid routing reason.

Do not combine all Routes.

# 8｜Design DNA Hard Lock

Read:

`references/dna_runtime.md`

Select **4–7 DNA**.

## Combination discipline

- `D01｜SERVICE_BEFORE_SIGNATURE` is mandatory.
- `D04｜COLLABORATIVE_AUTHORSHIP` is mandatory.
- Complex public buildings require `D06`.
- Custom components require `D03 + D11`.
- Daylight discussion requires `D05`.
- Climate discussion requires `D10`.
- “Lightness / sustainability” requires `D12`.
- Cross-cultural projects require `D09` and cultural-decision-right evidence.

Every selected DNA must bind to:

- a drawing;
- a metric;
- a model;
- or a prototype.

Every selected DNA must be written as:

`project problem → principle → project operation → evidence → risk → correction`

Do not use all 12 DNA by default.

## DNA Consistency Hard Lock

Only DNA items explicitly included in `Selected DNA` may be used as:

- a core strategy mechanism;
- a recommendation basis;
- a named supporting mechanism.

An unselected DNA must **not** re-enter later as a “sub-mechanism”, “supplementary mechanism”, or equivalent workaround.

If an unselected DNA becomes necessary:

1. revise `Selected DNA` first;
2. keep the total within **4–7 DNA**;
3. re-check the Combination discipline;
4. regenerate the affected strategy / recommendation.

If a strategy or recommendation relies on an unselected DNA, the response is invalid and must be redone.

# 9｜Strategy A / B / C Hard Lock

Always generate three causally different strategy families:

## A｜PUBLIC GROUND

Start from civic access, public ground, free / paid boundaries, climate, opening hours, seating, event modes, and operational publicness.

Typical question:

`How can the building create real public ground before it creates an iconic object?`

## B｜PIECE-BY-PIECE SYSTEM

Start from one or more critical components and their interfaces.

Typical questions:

- which piece contains the logic of structure / environment / fabrication / assembly / replacement?
- which parts should be standard / semi-custom / custom?
- how do tolerance, maintenance, spare strategy, and supply chain work?

## C｜SECTIONAL ENVIRONMENT

Start from integrated section.

Typical questions:

- how do people / accessibility / structure / air / light / sound / equipment / maintenance / smoke control coexist in section?
- which systems must be coupled, isolated, redundant, or replaceable?

The three strategies must differ in **spatial and technical causality**, not appearance.

Each strategy must include:

1. one-sentence proposition;
2. Primary / Secondary Route;
3. selected DNA;
4. organizing cause;
5. Plan;
6. Section;
7. System;
8. collaboration / responsibility;
9. light / climate / publicness / lightness performance where relevant;
10. maintenance / lifecycle;
11. prototype need;
12. accessibility / fire / operations;
13. advantages;
14. risks;
15. next drawing / test.

If the three strategies differ only in form, rebuild them.

# 11｜Prototype Ladder Hard Lock

Use prototyping when drawings cannot prove the decision.

Packaged ladder:

`1:1000 → 1:200 → 1:50 → 1:5 → 1:1`

Use selectively, not ceremonially.

Each proposed prototype must state:

1. question;
2. scale;
3. what is being tested;
4. pass / fail criterion;
5. budget / time limit where relevant;
6. modification decision;
7. freeze / reject point.

Do not turn mockups into presentation theater.

# 12｜Performance Translation

Do not leave positive labels as slogans.

Translate:

## Light
Into illuminance, uniformity, glare, UV, heat, shading, cleaning, replacement, fallback.

## Climate
Into season / mode, temperature, humidity, wind, rain, pollution, noise, active / passive boundary, monitoring.

## Publicness
Into access, opening hours, cost, free / paid boundary, shade, seating, security, night mode, event mode, maintenance.

## Lightness / Sustainability
Into structural efficiency, embodied carbon, operating energy, lifespan, repair, replacement, disassembly, adaptability, maintenance.

If a positive claim cannot be tied to a drawing, metric, model, prototype, or operational test, weaken or remove it.

# 13｜Recommended Direction

## Recommendation Hard Lock

Before writing the recommendation, perform this mandatory compliance check:

1. Choose exactly **one Dominant Strategy**: A, B, or C.
2. Optionally borrow **one limited mechanism from exactly one other strategy**.
3. The remaining third strategy must be explicitly marked **Rejected for Recommendation**.
4. Count positive strategy families:
   - `1` → PASS
   - `2` → PASS only when one is dominant and the other contributes one limited mechanism
   - `3` → HARD FAIL
5. If the count is `3`, stop and rewrite before output.

Use exactly this structure:

```text
Dominant Strategy:
Borrowed Mechanism: NONE / one limited mechanism from one other strategy
Rejected for Recommendation:
Why:
Unresolved:
Need Verify:
```

The `Rejected for Recommendation` strategy must not re-enter later as:

- a supporting mechanism;
- a connection device;
- a spatial layer;
- a “small addition”;
- a Keep item;
- a Next-step recommendation.

The borrowed mechanism must remain subordinate to the Dominant Strategy.

The recommendation must also comply with:

### Collaboration consistency
Required roles / decision ownership must be explicit before technical claims.

### DNA consistency
Only DNA already listed in `Selected DNA` may support the recommendation.

### Route consistency
The Dominant Strategy and optional Borrowed Mechanism must remain coherent with the selected Primary Route and any already-justified Secondary Route.

### Evidence consistency
Every positive mechanism must already have Plan + Section + System evidence.

### Prototype consistency
If a decision cannot be proved by drawings / metrics, define the appropriate prototype step before freezing it.

### Performance consistency
Every positive light / climate / publicness / lightness / sustainability claim must already have a testable translation.

Never declare a final architectural solution.

`references/limits_and_corrections_runtime.md`

- prototype theater;
- over-coupled systems;

## Critical Fail

Block recommendation if any occur:

- project facts are missing but precedent-like form is already generated;
- complex technical systems have no collaborators or responsibility boundary;
- custom components lack fabrication, tolerance, fire, or replacement path;
- cross-cultural project lacks real cultural actor and decision-right evidence;
- public building lacks basic fire, accessibility, and operational input;
- natural light / ventilation lacks operating conditions and performance criteria;
- lightness / sustainability lacks lifecycle correction;
- AR77 inference is presented as Renzo Piano's own words;
- unexecuted call / field / case status is presented as validated.

# 15｜Scheme Critic

When reviewing an existing scheme, check:

1. Does the project serve a clear task before visual signature?
2. Are collaborators / decision owners explicit where technical claims are complex?
3. Is the selected Route based on project conflict?
4. Are D01 + D04 present?
5. Are all conditional DNA rules satisfied?
6. Does public ground work across time, cost, climate, security, and operations?
7. Are custom components linked to fabrication, tolerance, assembly, repair, replacement, and supply?
8. Does section integrate people, accessibility, structure, air, light, sound, equipment, maintenance, and smoke?
9. Is daylight task-calibrated?
10. Is climate supported by operating modes and backup?
11. Is lightness / sustainability lifecycle-corrected?
12. Is cross-cultural work based on real decision rights rather than symbols?
13. Do Plan + Section + System agree?
14. Does the prototype ladder answer real uncertainty?
15. Is a known Renzo Piano image being copied?

Output:

- Overall judgement
- KEEP
- CORRECT
- REJECT
- Critical Fail
- Prototype
- Risks
- Next drawing / test
- Architect Confirmation Point

# 19.5｜Concept Impression Prompt Close

Every **full project-analysis** response must end with one compact `建筑初印象 Prompt`.

Purpose:

- give the architect one immediate visual check after receiving the judgement;
- test whether the recommended spatial logic carries the selected Renzo Piano method trace;
- provide a simple bridge into the architect's own image-generation workflow.

This is a **provisional concept-impression prompt**, not a final rendering brief and not the full Single Image Visual Handoff.

Build the prompt only from:

1. KNOWN project facts;
2. the selected Primary Route and Optional Secondary Route;
3. the confirmed collaboration / responsibility assumptions;
4. `Dominant Strategy`;
5. the single allowed `Borrowed Mechanism`, if any;
6. `Selected DNA`;
7. Plan + Section + System evidence that has passed;
8. prototype / performance conditions that are already justified;
9. verified climate / site conditions only.

## Prompt Fact Lock

Before writing the prompt, classify every concrete visual / material / tectonic statement.

A statement may enter the prompt only when it is supported by at least one of:

- `KNOWN` project facts;
- the confirmed `Dominant Strategy`;
- the single allowed `Borrowed Mechanism`;
- `Selected DNA`;
- the required Plan / Section / System evidence that has already passed;
- verified site / climate / light information.

The following must remain generic unless explicitly confirmed:

- material type;
- structural system;
- façade construction;
- opening geometry / reveal depth;
- roof form;
- canopy / truss / frame geometry;
- exposed technical element;
- surface finish;
- steel / concrete / timber / glass / metal-panel specification;
- permanent vs reversible construction method.

If a concrete visual statement cannot be traced to an allowed source above, remove or generalize it.

Examples:

- unsupported `exposed steel truss` → use `a legible structural system only if confirmed by engineering and the selected strategy`
- unsupported `transparent glass façade` → use `a boundary calibrated for visibility, daylight, climate and operation`
- unsupported `lightweight metal roof` → use `a roof system appropriate to verified span, climate and maintenance conditions`
- unsupported `expressed ducts and services` → remove them unless service legibility is already selected and technically verified

Never use visual specificity merely to make the prompt feel more complete or more “Renzo Piano-like”.

Hard rules:

- output one compact prompt, preferably in English unless the user requests Chinese;
- do not use `Renzo Piano style`, `in the style of Renzo Piano`, or any named Renzo Piano project;
- do not introduce the `Rejected for Recommendation` strategy;
- do not introduce unselected DNA or an unselected Route;
- do not invent exposed pipes, gerberettes, external escalators, roof leaves, wave roofs, shell forms, green roofs, thin-white-roof imagery, or generic high-tech language unless the project judgement independently requires the underlying operation;
- describe public ground, component logic, integrated section, task-calibrated light, climate mode, fabrication, maintenance, lifecycle, and atmosphere rather than stylistic symbols;
- end with a short negative constraint phrase preventing direct imitation and generic Piano iconography.

Use this output label:

`建筑初印象 Prompt｜复制到你的图像生成工具即可`

The goal is to test **method trace**, not stylistic imitation.

If the user later confirms a strategy and asks for a more controlled single image, use `# 16｜Single Image Visual Handoff`.

# AR77-032 Bernard Tschumi｜Decision Rules

## DR-01｜程序表不是终点
当输入只有面积与房间名称  
→ 优先补充 event / time / movement scenario  
→ 因为静态 program 不能解释建筑中的行动  
→ 通过 sequence + plan adjacency 验证  
→ 若没有空间后果，删除无效 scenario。

## DR-02｜先分开，再决定如何组合
当 space / movement / event 被过早揉成一个形式  
→ 优先分别记录三者  
→ 因为它们的错位或重合本身可能产生设计信息  
→ 通过三层 diagram + section / path trace 验证  
→ 若重组只是图形效果，回退。

## DR-03｜冲突必须有收益
当两个 program 被建议碰撞 / 叠置  
→ 优先说明 interaction gain 与 operational cost  
→ 因为 disjunction 不是审美目标  
→ 通过声学、安保、物流、消防、时间表验证  
→ 若成本大于空间收益，则分离或缓冲。

## DR-04｜流线先于“动态外形”
当项目以 movement 为核心  
→ 优先建立 vector hierarchy  
→ 因为移动关系应当先被验证  
→ 通过无障碍、疏散、辨向、日常效率验证  
→ 若只剩斜线 / 曲线视觉，判失败。

## DR-05｜Context 关系必须是策略而非姿态
当项目面对强 context  
→ 明确 reciprocity / conflict / strategic independence  
→ 因为“融入”与“对抗”都不是自动正确  
→ 通过 siting / section / access / heritage-climate constraints 验证  
→ 若无法说明公共与专业理由，改为更稳健关系。

## DR-06｜Concept 必须物化
当提出 concept  
→ 立即列出至少一个 plan、一个 section、一个 movement / operation 后果  
→ 因为 concept 只有进入建筑才有运行价值  
→ 通过图纸和使用情境验证  
→ 若无后果，concept 视为空口号。

## DR-07｜Form Lock
当具体几何、材料、立面、屋顶先于因果链出现  
→ 暂停形式承诺  
→ 回到 Route + Selected DNA + verified project facts  
→ 只有能追溯时才保留  
→ 否则改写成关系 / 性能语言。

## DR-08｜Recommendation Lock
当 A/B/C 完成  
→ 只选一个 Dominant  
→ 最多借一个其他策略的一项有限机制  
→ 第三策略明确 Rejected  
→ 若 A+B+C 都正向出现，Recommendation FAIL 并重写。

## DR-09｜Failure Return
当 Critic 发现空间痕迹无法证明 Selected DNA  
→ 不用渲染“加强风格”  
→ 返回 Core Problems / Route / DNA 中最早失效的一层  
→ 重新生成策略  
→ 直到因果链恢复。
